# Claude Eval Console

本地可视化工具，用于从空 GitHub 仓库开始运行容器化开发任务，完成逐轮检查、Bug 修复和交付整理。

## 功能

- 点击“新建任务”后，按四位项目编号生成唯一仓库名、单段第一轮 Prompt 和验收命令，复核通过后自动打开 Mac 终端；编号只写入 `0001-项目名` 形式的文件夹名称，不进入题面正文
- 每条任务新建独立的本地目录、`screen` 终端会话和 Docker 容器，容器内工作目录固定为 `/workspace`
- 0-1 任务会在 `makabaka-boop` 下创建公开仓库，首个提交只包含空 `README.md`
- 每 10 个编号包含 4 个纯后端、3 个纯前端和 3 个全栈项目，所有题目均要求使用 Docker Compose 运行与验收
- 出题时每批生成 2 个候选，本地硬校验并按范围负担择优；只有整批都不合规时才生成第 2 批。首选题独立复核不通过时保留备选题：与历史题实质重复就直接换候选，其他硬问题最多定向改写一次，改写时携带完整范围统计和硬约束。整段出题流程最多运行 15 分钟；任务失败后保留原编号和失败原因自动重试一次，用户取消不计入自动补题失败。历史题先压缩为摘要，生成阶段最多携带 15 条，复核阶段只比较最相近的 10 条。0-1 题面目标约 450 字，生成提示要求 300 至 520 字，本地硬校验接受 300 至 600 字；题目必须有且只有一个可独立验收的工程核心和一条主要纵向链路，范围限于 3～4 个实现模块、最多 2 个应用运行组件、最多 2 项核心外辅助机制、全题最多 1 项复杂状态机制、最多 1 种自定义算法体系以及 3～6 个验收场景，其中复杂状态机制与自定义算法不能同时出现。同一次操作下只产生同一个最终结果的多项检查合并为一个验收场景。会导致核心验收结果不唯一的规则、机制堆叠和无职责基础设施属于硬错误；开头、结尾、通用交付项位置及次要实现选择只参与择优或作为复核建议，不单独阻断。任务创建时不预设难度，最终难度仍由开发轨迹和产物决定；题目不能以普通 CRUD、审批、档案、认领、留痕或泛化“XX 管理系统”为主体，也不叠加分布式架构、复杂求解器、完整编译器、重型调度或多套高并发机制
- 已创建的首轮题面会自动追加到 `history-prompts.md`；即使 SQLite 记录迁移，后续出题仍会读取这份文档参与查重
- 保存初始 commit permalink
- 可在页面统一切换 Claude Code 模型，新容器启动时会把选中值传入容器
- 最多同时运行 6 个项目，超出的任务自动排队
- 终止只作用于当前记录的容器和终端，不处理其他 Claude 会话
- 每轮 Claude 交付后先运行验收，再创建并推送独立 Git 检查点；提交正文固定写入 `Session-ID`、`Turn-Number` 和 `Turn-ID`（即 PromptID），随后导出截至该轮完成边界的轨迹，全部成功后才使用 `gpt-5.6-sol` 找 Bug。Docker Compose 验收按运行记录使用独立项目名和动态宿主端口，结束后只清理该项目，避免不同任务互相复用容器或抢占端口
- 运行期间的日常监控只读取容器状态、轨迹变化和终端当前画面，不发送心跳、测试消息，也不会代替用户确认业务执行；发现操作确认、按键确认或补充指令提示时，列表立即显示“等待人工确认”，macOS 宿主机每 60 秒播放一次系统提示音，提示消失后继续普通监控。响铃和状态更新都发生在控制台侧，不产生新的 User Prompt、TurnID 或轨迹事件；连续 30 分钟无新活动仅提示。只有终端明确回到任务完成后的空闲界面并连续保持 5 分钟、轨迹仍缺少可归档最终回复时，才自动催收一次；催收后至少等待 120 秒，仍无合格回复且终端再次稳定空闲，才保留代码和轨迹并关闭运行环境
- 容器在交付前退出时自动保留本地代码、导出轨迹并标记为中断，可从原始快照创建全新容器和 SessionID 重跑
- 任一 Claude 开发轮遇到 408、429、500、502、503、504 等临时 API 错误时，先保留容器并在原 Session 自动输入一次“继续”；恢复后沿用已有上下文、代码和轨迹完成当前轮。发送后等待 30 秒仍未恢复，或同一轮再次出现临时 API 错误，才归档现场并从该任务初始快照使用新会话重跑，最多 2 次；只按 `retries/retry-01`、`retry-02` 计算新会话重跑次数，原会话的“继续”不占次数，0-1 与 Feature 的项目迭代层级也不占用次数。重跑目录归入原编号的 `retries/retry-XX`，不占用下一道题编号；用户主动中断以及 401、403 等鉴权或权限错误不会自动输入“继续”，只提示人工处理
- Claude 输出本轮最终回复后，控制台立即把该轮标记为“完成/会话空闲”，交互容器继续存活；Git 推送、轨迹检查点或复核遇到临时网络故障时按退避时间自动重试两次，仍失败时保留现场并提供“重试当前阶段”，不会发送下一轮题面。上游接口临时中断后自动发送的“继续”属于同一逻辑轮次，轨迹检查点会保留中断前后的完整事件和恢复后的最终回复；轨迹尚未落盘也会自动重试，不再直接判定运行失败。复核过程误把控制台验收命令写进五维描述时，系统会自动改成不冒充开发过程的验收表述；旧版本因此中断且已形成 Git 检查点的任务会在重启后重新进入原复核阶段，不会让远端新提交失去可用基线
- 找 Bug 从该轮已推送 commit 创建一次性隔离工作区，允许执行复现命令但不回写 Claude 工作目录；Bug 与质量缺口先单独检查并持久化，再通过第二次结构化调用生成五维评分，避免一份大输出超过响应上限。评分输出临时中断时复用已经保存的 Bug 结论并只重试评分。每个 Bug 必须给出稳定复现步骤、实际结果、预期结果以及命令、响应、日志或数据库状态证据；未复现风险、缺少测试、覆盖不足、文档不足和代码结构问题只记为质量建议，不触发 Bug 修复轮
- 确认真实 Bug 后，修复题面始终发送给同一个容器、终端和 SessionID，并产生新的 TurnID；完成后再次按“验收 → Git 提交并推送 → 轮次轨迹导出 → 复查”执行，直到没有真实 Bug 或达到 10 轮上限
- 没有确凿 Bug 时导出完整会话轨迹，再关闭 Claude 会话并删除本题容器；各轮检查点已经提前推送和导出，不在最终检查阶段重复提交
- 后续迭代必须从已通过检查的 commit 快照新建任务，使用新目录、新容器、新终端和新 SessionID，不续接 0-1 对话；目录沿用源项目主编号并追加迭代序号（如 `0003-1-项目名`、`0003-2-项目名`），不占用下一道 0-1 新项目的四位主编号
- 每一轮都单独保存 User Prompt、PromptID、Git commit、轨迹文件、轨迹 SHA-256、模型、返回结果、Docker 验收、任务类型、难度、环境等级、五维评分和具体依据；五维评分直接读取 `doc.md`“第三步”的 1～5 分档标准，禁止换算为其他分制，分数和描述必须与本轮轨迹、产物证据一致；任务创建时难度为“待评估”，0-1、迭代和 Bug 修复均在该轮结束后由检查模型依据真实轨迹、代码产物与验收结果判定；`traces/<SessionID>/manifest.json` 记录轮次、提交和轨迹哈希的对应关系
- 切换模型后，新任务和尚未启动容器的排队任务使用新模型；已启动的容器为了保持原 SessionID 不中途切换
- 详情页按轮次展示所有 PromptID、模型、完整题面、执行结果和检查结果
- 详情页记录初始仓库、第一轮开发、首轮检查、后续轮开发和逐轮复查的累计耗时，当前环节每分钟更新
- 运行记录页可按编号或关键词、任务类型、项目类别和状态组合筛选；终态记录可从列表隐藏，数据库采用可恢复的软删除，本地项目与 GitHub 仓库始终保留。有后续迭代记录时须从最末端开始处理
- “导出完成轮次”页面列出所有状态为完成的轮次，每行最左侧可展开查看该轮完整题面，并逐项校验真实 SessionID、PromptID、40 位 Git commit、GitHub commit 快照、轨迹文件及 SHA-256、五维评分和数字 Harness 版本。有评分的轮次均可勾选生成真实 `.xlsx` 复核副本；资料缺项会在页面标出并阻止人工确认和正式提交。每个轮次占一行，最前面固定为“编号”和“项目 / 仓库”，随后是详情页“复制交付信息”的字段，文本会进行 Excel 公式注入防护
- 进入导出页时立即读取一次完成轮次，停留期间每 5 分钟自动更新；运行记录与环境状态仍按 3 秒刷新。任务列表和导出列表默认每页显示 20 条，表格上方、下方都能切换页码；筛选后返回第一页，自动刷新时保留仍然有效的当前页。展开轮次后的五维描述输入框默认显示 6 行并允许继续向下拉伸
- 导出页面可通过随仓库提供的 Chrome 提交助手同步 SOLO-QA“我的提交”，以 SessionID、TurnID 和轮次匹配历史记录；选择一个或多个合规轮次后，可自动读取远端最新表单结构、上传已校验摘要的轨迹、逐条提交并把质检状态和远端编号写回本地。批量操作遇到首条失败即停止，网络结果不确定时先回查远端，已提交轮次不会盲目重复创建
- 可配置每轮结束后的验收命令
- 本地 SQLite 保存任务和运行轨迹

## 启动

```bash
cd "/Users/zhangxinyu/claude code/claude-eval-console"
python3 app.py --open
```

默认地址为 <http://127.0.0.1:8765>。

## macOS 常驻启动

本机使用 LaunchAgent `com.local.claude-eval-console`。它会在用户登录后自动启动，服务异常退出时自动重启，且始终只监听 `127.0.0.1:8765`。

查看状态：

```bash
launchctl print gui/$(id -u)/com.local.claude-eval-console
```

手动重启：

```bash
launchctl kickstart -k gui/$(id -u)/com.local.claude-eval-console
```

服务日志位于 `.data/server.stdout.log` 和 `.data/server.stderr.log`；带运行编号与阶段的工作流异常写入自动轮转的 `.data/workflow.log`（最多保留 3 个历史文件）。

控制台自身检查：

```bash
pytest -q
node --check static/app.js
node tests/test_solo_helper.mjs
python3 -m py_compile app.py
```

启动前需要确认 Docker Desktop 已启动，并准备好本次任务的 API Key：

```bash
gh auth status
docker info
codex --version
git --version
```

export CLAUDE_EVAL_DOCKER_IMAGE="claude-eval-runtime:claude-2.1.269"
export CLAUDE_EVAL_MAX_PARALLEL="6"
export CLAUDE_EVAL_HARNESS_VERSION="2.1.269"
export CLAUDE_EVAL_SUBMITTER="刘昱"
export CLAUDE_EVAL_ARTIFACT_NODE="/path/to/codex-primary-runtime/dependencies/node/bin/node"

本机派生镜像保留原任务入口、Node 20 环境和非 root 用户，只更新 Claude Code 原生程序。重新构建固定版本：

```bash
docker build -t claude-eval-runtime:claude-2.1.269 \
  --build-arg CLAUDE_CODE_VERSION=2.1.269 \
  docker/claude-runtime
```

模型下拉框默认提供 Default、Opus 1M、Sonnet、Sonnet 1M 和 Haiku，并合并当前全局模型及 `CLAUDE_EVAL_MODELS` 中以逗号分隔的自定义模型。默认镜像已配置 `auto_model/urm`，启动脚本同时使用 `ANTHROPIC_MODEL` 传入当前选择。新任务启动时会依次尝试 `CLAUDE_EVAL_DOCKER_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_API_KEY` 和 `~/.claude/settings.json` 里的本机认证配置，只把取到的值传入本题容器，不写入页面、SQLite 或启动脚本。只有自动读取失败时，Terminal 才会要求手动输入。页面只监听 `127.0.0.1`。

运行记录是默认页面，列表直接展示任务开始时间和最近更新时间，并支持按当前对话轮次、开始时间和更新时间排序；语言 / 框架与模型不占用列表列位，仍可在记录详情中查看。页面还可通过编号或关键词、任务类型、项目类别和状态筛选。点击“新建任务”后会在 `0001–2999` 号段预留下一个未使用编号并立即在列表写入“题目生成中”，题面在后台生成并原地补全同一条记录；刷新页面不会丢失进度，同一生成任务未结束时重复请求只返回原记录。自动迭代尚在生成题面、还没有创建正式项目时，也会以蓝色“待创建 / 题面生成中”只读占位行出现在列表；占位行显示来源项目和当前生成阶段，点击可查看来源任务，通过校验并创建正式任务后会被真实记录自动替换。题目生成失败时，详情页会保留具体校验原因并提供“沿用原编号重新生成题面”，重试不会消耗新的顺序号。该号段中的顶层 `NNNN-*` 目录会占用普通新项目编号，`3000–3999` 导入号段不会把下一道普通题跳到 3001。点击记录进入详情后，可直接查看完整题面、技术信息和验收命令，并通过浏览器后退或页面按钮返回列表。列表删除只做软删除，不删除轮次证据、本地目录或远端仓库；运行中的记录不可删除，存在子迭代时会返回明确提示。误删可调用 `POST /api/runs/<run_id>/restore` 并发送空 JSON 对象恢复。

顶部使用“运行记录 / 导出轮次 / 数据分析”三个 Tab。数据分析页默认按上海本地日期展示 24 个自然小时的完成轮次总量、峰值时段、活跃小时、全天均值和任务类型分布，也可切换日期查看历史产出。0-1、Feature、Bug 修复和其他类型的当天总条数使用与核心指标一致的概览卡片展示。小时趋势可在柱状图与折线图之间切换；鼠标悬浮或键盘聚焦图表标记时，会显示该时段的总量和各任务类型明细。统计只计入 `status = complete` 的真实完成轮次；从导出列表软隐藏的轮次仍属于已经发生的产出，因此继续计入。

运行记录页的“导入现有 0-1 基线”用于登记在本机完成、准备继续出迭代题的项目。页面只需填写一个或多个 `3000–3999` 编号以及保存分组，例如 `3000, 3001`；控制台按编号寻找唯一的顶层项目目录，自动读取 README、项目类别、语言/框架、GitHub commit 和 Docker Compose 验收入口。导入只接受位于 `CLAUDE_EVAL_PROJECTS_ROOT` 内、README 信息足够、工作树干净、`origin` 指向 GitHub、当前 HEAD 与远端 `main` 一致且 `docker compose config --quiet` 通过的仓库。已登记编号重复提交时直接返回原记录；同批其他编号失败不会回滚已经成功的项目，页面会逐项写明缺失目录、README、Git 或 Compose 等原因。导入记录没有 Claude 会话，因此不会伪造 SessionID、PromptID、轨迹或可导出轮次；它只保存 GitHub 初始快照并作为手动迭代和自动补题的根基线，后续目录继续使用 `3000-1`、`3000-2` 等编号。

页面顶部的“自动补题”开关默认关闭，状态和保存目录写入 SQLite，控制台重启后保持不变。关闭状态下可以输入 0.5～168 小时预约开始，页面显示开始时刻和倒计时；到点后协调器自动开启补题，也可以更新预约、取消预约或提前立即开启。开启状态下可以输入 0.5～168 小时设置定时关闭；关闭时刻同样持久化，页面显示具体时间和剩余时长，到点只停止创建新任务，已经启动的开发任务继续运行。也可以更新或取消关闭定时，改为持续开启。开启后，协调器每 5 秒检查一次容量，把手动题面生成、自动出题、开发、检查和修复共同计入最多 6 个并行槽；已经确认的后续 Bug 修复沿用原任务并优先取得空槽。仍有容量时，系统优先从已完成且有效任务数不足 6 的根项目中继续出题，失败或中断且没有产物的任务不消耗额度，重跑成功只按原任务计一次；同一项目链同时只运行一个独立任务。若 SOLO-QA 将任一轮标为需要返修或废弃，且质检原因明确命中雷同题库、常见小应用或项目/题目/题面/选题/题材不合格，整条根项目链都会退出手动及自动补题选源；普通的内容返修不会误伤项目链。自动链在第 1、4 个位置生成 Feature，第 2、5 个位置生成基于现有代码的 Bug 修复题，第 3、6 个位置可以穿插完整模块构建；每条链最多两个 0-1 完整模块且不能连续出现。Bug 修复题仍须先复现三至四个范围适中的真实问题，并在内部保存 reproduction、actual、expected、evidence 和小或中的修改范围。开发者最终看到的题面只由项目专属范围说明和各问题的自然 customer_summary 组成：不添加固定开头，不套用“当……当前表现……正确结果……”句型，也不追加回归测试、Docker Compose 或范围免责尾巴；容器验收继续由控制台内部执行和保存。摘要中的编号、引号、连续标点和多余句末符号由本地程序直接整理，不再让整次候选生成失败；真实复现证据、项目关联、实现方案泄露和历史实质重复仍按硬条件检查。Bug 题面生成的单次检查最多运行 15 分钟，超时、实质字段缺失或复核异常会携带失败原因再生成一次；两次仍失败时让该来源冷却 30 分钟并继续选择其他来源。单纯的长度、措辞或独立复核不通过属于候选质量问题，会清零平台故障计数，不再暂停整个队列；只有连续 3 个超时、模型调用、连接或任务执行等系统性失败才暂停全局补题，暂停后已经在途的结果不会继续增加计数或覆盖暂停原因。完整模块候选未通过时自动退回范围更小的 Feature。没有合适来源时才创建新的顶层 0-1 项目。顶层 0-1 出题每次生成 2 个候选并本地择优，独立复核不通过时只按原题定向改写一次；页面显示候选生成、独立复核和定向改写进度。新题面禁止出现待办清单、任务清单等常见小应用题材，也不再写出容易被题库分类器误判为待办应用的英文占位词，统一改写为“占位实现”。

完成轮次导出页支持按编号或项目、任务类型、难度、资料状态、SOLO-QA 状态和完成日期范围组合筛选；表头全选只作用于当前筛选结果，筛选前已勾选的其他轮次会保留并在计数中注明。单条“删除”和“删除所选”只把完成轮次从导出列表软隐藏，不删除运行记录、项目代码、GitHub 仓库、轨迹证据或 SOLO-QA 远端提交，可通过 `POST /api/exports/turns/restore` 携带 `turn_keys` 恢复。完成轮次导出依赖 Codex 桌面环境附带的 Node.js 与 `@oai/artifact-tool`。默认会从 `~/.cache/codex-runtimes/codex-primary-runtime/dependencies` 读取，也可使用 `CLAUDE_EVAL_ARTIFACT_NODE` 和 `CLAUDE_EVAL_ARTIFACT_NODE_MODULES` 指向兼容运行时。导出失败会返回结构化错误，不会生成空文件或 CSV 伪装的 Excel。

独立 Bug 修复的候选通过复核后，控制台会把来源任务、来源提交、复核时间、逐项 reproduction、actual、expected、evidence、修改范围、客户摘要和独立复核结论一起保存到新任务记录；开发者仍然只看到自然题面，后续重跑继续沿用原始证据。

## 提交到 SOLO-QA

首次使用需要安装本地 Chrome 提交助手：

1. 在 Chrome 打开 `chrome://extensions` 并开启“开发者模式”。
2. 点击“加载已解压的扩展程序”。
3. 选择 `/Users/studio1/Library/Application Support/Claude Eval Console/chrome-solo-qa-helper`。
4. 登录 <https://solo2.jzxhnh.com>，然后刷新 <http://127.0.0.1:8765/#exports>。

导出页显示“提交助手已连接”后不会自动遍历历史记录，页面直接使用本地保存的最近状态；需要核对质检结果或处理返修时，再点击“同步并自动返修”。同步只读取北京时间当天的提交并读取详情，翻页遇到更早日期后立即停止，再用 SessionID 与 TurnID/PromptID 精确匹配本地完成轮次；因为不再遍历完整历史，这个快速同步不会据此判断旧记录是否已被远端删除。对于质检原因能由本轮题面、轨迹和验收结果安全修复的待返修项，系统只重写命中维度的公开描述，重新执行提交前检查，再更新原 SOLO-QA 记录；分数和内部证据保持不变，缺少证据、修复失败或检查不通过的记录继续留给人工处理。正式提交只对本次所选且本地尚未提交的轮次按相同标识做精确回查，不重复核对已经质检通过的历史记录；同批轮次复用一次远端表单结构，提交成功后先记为质检中，后续状态由同步更新。

选择轮次后点击“提交所选轮次”，确认弹窗中列出的编号、仓库和轮次。助手会动态获取 SOLO-QA 当前表单 fingerprint，将本地任务类型转换成远端规范值，校验并上传不超过 20 MB 的轨迹，再按顺序提交。状态包括未提交、提交中、质检中、质检通过、需要返修、已废弃、提交失败、远端未找到和本地数据已变化。不能安全自动处理的退回项仍可按质检原因人工修改，再点击“返修所选轮次”；助手只处理仍关联原远端 ID 且远端状态为待返修的记录，上传当前轨迹并更新原记录，不创建重复提交。批量任务的一条记录失败后会继续处理其他独立记录，同一会话的后续轮次会留到前序轮次成功后再处理。远端读取遇到临时网络故障会短暂退避重试；轨迹上传和远端更新不盲目重发，并会回查状态，避免响应丢失时重复返修。更新扩展代码后需要在 `chrome://extensions` 重新加载扩展并刷新导出页。

扩展的权限只覆盖 `http://127.0.0.1:8765/*` 和 `https://solo2.jzxhnh.com/*`。它使用 Chrome 当前的 SOLO-QA 登录状态，不读取或保存账号、密码和 Cookie；只有点击“提交所选轮次”并确认，或点击“同步并自动返修”且存在可安全处理的退回项时，才会上传轨迹并写入远端。

详情页的“复制交付信息”、导出页、Excel 和 SOLO-QA 统一读取同一份有效评分；存在人工覆盖时优先显示人工版本，原始自动评分与内部证据保持不变。人工确认会绑定当前评分、Git commit、轨迹摘要、验收结果、SessionID 和 PromptID，任一内容变化后确认立即失效；SOLO-QA 正式提交还要求项目进入终态并完成容器和终端收尾。Excel 仅作为复核副本，旧数据不会自动获得人工确认。固定字段包括 Prompt、SessionID、PromptID、轮次、本轮 Git commit、GitHub 初始快照、永久轨迹路径、环境信息、任务元数据和五维评分。提交人由 `CLAUDE_EVAL_SUBMITTER` 配置，Harness 版本从任务所用镜像读取并保存纯数字版本。

评分按交付完整性、指令遵循、任务规划、推理能力、执行能力的固定顺序独立定档，只评价可见操作、说明、决策和产物。义务来源限于实际题面与有效上下文，后续验收计划不能反推为原作业漏项；虚假成功必须同时有面向使用人员的完成声明和工具输出或产物反证。后续同类检查决定当前产物状态，但不会抹掉原作业已经发生的失败、漏验或虚假声明。环境、网络、权限及复核工具故障可以记录，但不能作为能力扣分依据；项目锁文件、依赖清单等仓库错误仍按产品事实处理。

每条新版评分保存 `score_stage_version=2`，并按五维固定顺序保存 `scores`、`descriptions`、`when`、`behavior`、`impact`、`expected` 和 `evidenceRefs`，另存 `processFindings` 与 `artifactFindings`。`when` 明确第几轮、第几步和具体调用、命令或操作，`behavior` 点明真实文件名、函数名、命令或报错原文。每维证据引用限制为 1～8 个真实的 `文件路径:行号`：源码引用本轮 commit 的仓库相对路径，过程引用永久 JSONL 轨迹的原始行号；文件不存在、越过仓库或行号越界都会阻止该轮完成。旧评分没有这些字段时仍可读取和导出。

公开五维点评写成自然小段。非满分说明真实操作或场景、观察到的问题和已经造成的客观后果，不能用“如果上线可能”替代实际影响；页面问题优先写入口、控件、动作与可见现象。必要且有轨迹依据的命令和原始报错可以保留，后续验收命令必须明确标注来源。绝对路径、源码行号、哈希、内部报告名、精确测试总数和原始数字数组只放内部证据。系统不再自动把“未”改成“没有”或替换业务字段，避免润色改变事实。某一维未通过规则时只定向修正该维及其内部证据；连续修正仍不合规时不会把轮次标成完成。

## 完成后继续迭代

当 0-1 任务和它的全部 Bug 修复通过检查后，进入该任务详情页顶部的“新建独立迭代会话”，可以选择“完整模块构建（0-1 代码生成）”“平滑扩展（Feature 迭代）”或“现有问题整理（Bug 修复）”，再点击生成按钮。系统固定使用 `gpt-5.6-sol` 读取当前干净的 Git 工作树，以及从根任务到当前版本的完整迭代历史：0-1 类型要求在当前项目中从零形成此前不存在、可独立验收的完整纵向模块，Feature 类型要求复用既有核心对象并平滑扩展现有流程。每轮会保存扩展方向、工程核心、用户主流程、修改模块、复杂维度、接口或操作及状态集合，后续出题会同时比较这些结构化信息和完整题面，拒绝只换名称的重复状态、闸门、审批、导出或错误处理。已经失败、停止或中断且没有形成有效产物的迭代仍保留在历史中，但标记为 abandoned，不占六轮配额也不永久阻塞项目链；再次发起时系统重新读取远端 `main`。如果远端已经更新而历史工作区仍停留在旧提交，系统会在内部缓存中检出远端最新提交，历史工作区保持不动，新会话仍从最新代码开始。运行中的迭代仍会阻止重复创建。

Feature 与完整模块使用硬范围预算控制实现负担，但不在题面中写难度标签：题面统一为 300～480 字、四至六个完整句子、分号不超过两个且单句不超过 120 字；只涉及三至四个逻辑模块、一个工程核心、一条用户主流程、最多两个新增接口或用户操作、最多一组新增状态、一项复杂机制和三至四个验收场景。Feature 不得增加独立运行组件；完整模块最多增加一个独立运行组件，且不能与复杂机制同时出现。新的分布式协调、密码学证明、自定义二进制协议、复杂求解器或完整跨进程恢复不能作为迭代核心。生成结果先通过本地结构化硬校验，独立复核再从实际题面重新提取范围，不采信候选自报的数量；少报、合并机制、成功历史实质重复或模板化表达都会被退回。失败题面不被当作已经实现的功能，可以根据当前代码重新设计，但不会原样重发。题面按业务因果自然组织，不机械拼接数据库、接口、页面与测试字段，不连续堆叠命令句，不使用“沿用既有不变量”“其余失败沿用错误信封”等模板短语，也不在结尾集中罗列通用清单。内部范围筛选条件不会写进题面，出题模型与页面选择的开发模型相互独立。

独立 Bug 修复任务会先在最新成功代码上检查并复现问题，选择集中在同一用户流程、预计修改范围为小或中的三至四个真实 Bug。第一轮题面由项目专属范围说明和客户可读的问题摘要组成，只描述业务对象、触发条件、错误表现和正确状态，不给解决方法、技术实现或通用验收清单；无法稳定复现、属于环境故障或已经在成功历史中修好的问题不会进入题面。自动补题的六轮链默认在第 2、5 轮安排 Bug 修复，第 3、6 轮仍可安排完整模块，其余位置使用 Feature。开发完成后的检查若仍发现 Bug，后续修复轮直接按原顺序用中文分号连接问题摘要，不添加固定开场或编号。

Bug 检查的详细复现步骤、实际结果、预期结果和命令证据保存在检查记录中，不再全部塞进发给开发者的题面。每个 Bug 的客户摘要只用一句话说明项目对象、触发条件、当前可观察结果和正确状态，不自行添加标题、序号、引号、实现术语或通用测试清单；系统只负责保持原顺序并连接成无换行题面。同一问题修复后仍存在时，下一轮必须依据新证据描述修复后的残留状态；如果没有新的可观察差异，流程停止自动换词续轮并提示人工确认。

点击后接口立即把出题放入后台，任务状态和当前阶段同时写入 SQLite；页面刷新或控制台重启后会继续识别并恢复，运行中也可点“取消生成”。再次选择同一类型只会等待同一后台任务，已经创建过同类型产出时直接返回原运行记录。Feature、Bug 修复与 0-1 共用每条链最多 6 个有效独立任务的额度；完整模块最多两个且不能连续创建，手动选择和自动补题执行相同配额与全局六槽限制。每次生成题面和创建目录前，系统都会读取 GitHub 远端 `main` 的实际 HEAD；存在同提交的干净工作区时直接使用，否则把该提交克隆到内部只读基线缓存。新记录的 GitHub 初始快照和克隆 commit 始终指向实际远端 HEAD，不会从旧代码分叉，也不会改写历史任务的工作区。单个来源暂时无法准备基线时会进入冷却并跳过，不再立即关闭整个自动补题。生成通过后，系统会立即新建一条运行记录，打开新 Terminal，启动新容器和新 SessionID，再把该最新 Git commit 克隆到新的 `/workspace` 并执行需求；不续接旧对话，也不预先改变来源任务。生成或复核失败时不会创建半成品运行记录，错误会写入来源任务时间线并允许再次点击。任务完成后如果检查出真实且与本轮需求直接相关的 Bug，只在这个新 SessionID 中继续修复和复查；无关历史问题只记录为质量建议，不进入修复题面。

新任务默认保存在 `CLAUDE_EVAL_PROJECTS_ROOT` 指定根目录下的 `CLAUDE_EVAL_DEFAULT_DIRECTORY` 子目录；当前部署使用 `/Users/studio1/Library/Application Support/Claude Eval Projects/runs`。从空仓库创建的本地项目文件夹使用四位顺序号，例如 `0001-incident-handoff-board`、`0002-data-quality-console`；基于现有快照的新迭代使用源编号下的独立序号，例如 `0002-1-incident-handoff-board`、`0002-2-incident-handoff-board`。两类编号都不影响 GitHub 仓库名。
