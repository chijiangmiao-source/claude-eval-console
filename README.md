# Claude Eval Console

本地可视化工具，用于从空 GitHub 仓库开始运行容器化开发任务，完成逐轮检查、Bug 修复和交付整理。

## 功能

- 点击“新建任务”后，按四位项目编号生成唯一仓库名、单段第一轮 Prompt 和验收命令，复核通过后自动打开 Mac 终端；编号只写入 `0001-项目名` 形式的文件夹名称，不进入题面正文
- 每条任务新建独立的本地目录、`screen` 终端会话和 Docker 容器，容器内工作目录固定为 `/workspace`
- 0-1 任务会在 `makabaka-boop` 下创建公开仓库，首个提交只包含空 `README.md`
- 每 10 个编号包含 4 个纯后端、3 个纯前端和 3 个全栈项目，所有题目均要求使用 Docker Compose 运行与验收
- 出题时每批生成 2 个候选，本地硬校验并按范围负担择优；只有整批都不合规时才生成第 2 批。首选题独立复核不通过时保留备选题：与历史题实质重复就直接换候选，其他硬问题最多定向改写一次，改写时携带完整范围统计和硬约束。整段出题流程最多运行 15 分钟；任务失败后保留原编号和失败原因自动重试一次，用户取消不计入自动补题失败。历史题先压缩为摘要，生成阶段最多携带 15 条，复核阶段只比较最相近的 10 条。0-1 题面目标约 450 字，生成提示要求 300 至 520 字，本地硬校验接受 300 至 600 字；题目必须有且只有一个可独立验收的工程核心和一条主要纵向链路，范围限于 3～4 个实现模块、最多 2 个应用运行组件、最多 2 项核心外辅助机制、全题最多 1 项复杂状态机制、最多 1 种自定义算法体系以及 3～6 个验收场景，其中复杂状态机制与自定义算法不能同时出现。同一次操作下只产生同一个最终结果的多项检查合并为一个验收场景。会导致核心验收结果不唯一的规则、机制堆叠和无职责基础设施属于硬错误；开头、结尾、通用交付项位置及次要实现选择只参与择优或作为复核建议，不单独阻断。任务创建时不预设难度，最终难度仍由开发轨迹和产物决定；题目不能以普通 CRUD、审批、档案、认领、留痕或泛化“XX 管理系统”为主体，也不叠加分布式架构、复杂求解器、完整编译器、重型调度或多套高并发机制
- 已创建的首轮题面会自动追加到 `history-prompts.md`；即使 SQLite 记录迁移，后续出题仍会读取这份文档参与查重
- 保存初始 commit permalink
- 可在页面统一切换 Claude Code 模型，新容器启动时会把选中值传入容器
- 最多同时运行 4 个项目，超出的任务自动排队
- 终止只作用于当前记录的容器和终端，不处理其他 Claude 会话
- 每轮 Claude 交付后先运行验收，再创建并推送独立 Git 检查点；提交正文固定写入 `Session-ID`、`Turn-Number` 和 `Turn-ID`（即 PromptID），随后导出截至该轮完成边界的轨迹，全部成功后才使用 `gpt-5.6-sol` 找 Bug。Docker Compose 验收按运行记录使用独立项目名和动态宿主端口，结束后只清理该项目，避免不同任务互相复用容器或抢占端口
- 运行期间只读取容器状态和轨迹变化，不发送心跳或测试消息；连续 30 分钟无新活动仅提示，超过 6 小时仍不停止会话
- 容器在交付前退出时自动保留本地代码、导出轨迹并标记为中断，可从原始快照创建全新容器和 SessionID 重跑
- 任一 Claude 开发轮遇到 408、429、500、502、503、504 等临时 API 错误时，归档失败轨迹后等待 30 秒自动从该任务初始快照使用新会话重跑，最多 2 次；只按 `retries/retry-01`、`retry-02` 计算重跑次数，0-1 与 Feature 的项目迭代层级不占用次数。重跑目录归入原编号的 `retries/retry-XX`，不占用下一道题编号；401、403 等鉴权或权限错误只提示人工处理
- Claude 输出本轮最终回复后，控制台立即把该轮标记为“完成/会话空闲”，交互容器继续存活；Git 推送、轨迹检查点或复核遇到临时网络故障时按退避时间自动重试两次，仍失败时保留现场并提供“重试当前阶段”，不会发送下一轮题面
- 找 Bug 从该轮已推送 commit 创建一次性隔离工作区，允许执行复现命令但不回写 Claude 工作目录；必须给出稳定复现步骤、实际结果、预期结果以及命令、响应、日志或数据库状态证据；未复现风险、缺少测试、覆盖不足、文档不足和代码结构问题只记为质量建议，不触发 Bug 修复轮
- 确认真实 Bug 后，修复题面始终发送给同一个容器、终端和 SessionID，并产生新的 TurnID；完成后再次按“验收 → Git 提交并推送 → 轮次轨迹导出 → 复查”执行，直到没有真实 Bug 或达到 10 轮上限
- 没有确凿 Bug 时导出完整会话轨迹，再关闭 Claude 会话并删除本题容器；各轮检查点已经提前推送和导出，不在最终检查阶段重复提交
- 后续迭代必须从已通过检查的 commit 快照新建任务，使用新目录、新容器、新终端和新 SessionID，不续接 0-1 对话；目录沿用源项目主编号并追加迭代序号（如 `0003-1-项目名`、`0003-2-项目名`），不占用下一道 0-1 新项目的四位主编号
- 每一轮都单独保存 User Prompt、PromptID、Git commit、轨迹文件、轨迹 SHA-256、模型、返回结果、Docker 验收、任务类型、难度、环境等级、五维评分和具体依据；五维评分直接读取 `doc.md`“第三步”的 1～5 分档标准，禁止换算为其他分制，分数和描述必须与本轮轨迹、产物证据一致；任务创建时难度为“待评估”，0-1、迭代和 Bug 修复均在该轮结束后由检查模型依据真实轨迹、代码产物与验收结果判定；`traces/<SessionID>/manifest.json` 记录轮次、提交和轨迹哈希的对应关系
- 切换模型后，新任务和尚未启动容器的排队任务使用新模型；已启动的容器为了保持原 SessionID 不中途切换
- 详情页按轮次展示所有 PromptID、模型、完整题面、执行结果和检查结果
- 详情页记录初始仓库、第一轮开发、首轮检查、后续轮开发和逐轮复查的累计耗时，当前环节每分钟更新
- 运行记录页可按编号或关键词、任务类型、项目类别和状态组合筛选；终态记录可从列表隐藏，数据库采用可恢复的软删除，本地项目与 GitHub 仓库始终保留。有后续迭代记录时须从最末端开始处理
- “导出完成轮次”页面列出所有状态为完成的轮次，每行最左侧可展开查看该轮完整题面，并逐项校验真实 SessionID、PromptID、40 位 Git commit、GitHub commit 快照、轨迹文件及 SHA-256、五维评分和数字 Harness 版本；资料不全的行会显示原因且不能勾选。合规轮次可多选生成真实 `.xlsx`，每个轮次占一行，最前面固定为“编号”和“项目 / 仓库”，随后是详情页“复制交付信息”的字段，文本会进行 Excel 公式注入防护
- 导出页面可通过随仓库提供的 Chrome 提交助手同步 SOLO-QA“我的提交”，以 SessionID、TurnID 和轮次匹配历史记录；选择一个或多个合规轮次后，可自动读取远端最新表单结构、上传已校验摘要的轨迹、逐条提交并把质检状态和远端编号写回本地。批量操作遇到首条失败即停止，网络结果不确定时先回查远端，已提交轮次不会盲目重复创建
- 可配置每轮结束后的验收命令
- 本地 SQLite 保存任务和运行轨迹

## 启动

```bash
cd "/Users/zhangxinyu/claude code/claude-eval-console"
python3 app.py --open
```

默认地址为 <http://127.0.0.1:8765>。

## macOS 常驻启动

本机使用 LaunchAgent `com.makabaka.claude-eval-console`。它会在用户登录后自动启动，服务异常退出时自动重启，且始终只监听 `127.0.0.1:8765`。

查看状态：

```bash
launchctl print gui/$(id -u)/com.makabaka.claude-eval-console
```

手动重启：

```bash
launchctl kickstart -k gui/$(id -u)/com.makabaka.claude-eval-console
```

服务日志位于 `.data/server.stdout.log` 和 `.data/server.stderr.log`；带运行编号与阶段的工作流异常写入自动轮转的 `.data/workflow.log`（最多保留 3 个历史文件）。

控制台自身检查：

```bash
pytest -q
node --check static/app.js
node tests/test_solo_helper.mjs
python3 -m py_compile app.py
```

启动前需要确认 Docker Desktop 已启动，并准备好本次任务的 API Key：

```bash
gh auth status
docker info
codex --version
git --version
```

## 可选配置

```bash
export CLAUDE_EVAL_GITHUB_OWNER="makabaka-boop"
export CLAUDE_EVAL_PROJECTS_ROOT="/Users/zhangxinyu/claude code"
export CLAUDE_EVAL_DEFAULT_DIRECTORY="zzzz"
export CLAUDE_EVAL_MODEL="auto_model/urm"
export CLAUDE_EVAL_MODELS="auto_model/urm,model_hub/example-model"
export CLAUDE_EVAL_DOCKER_IMAGE="adminfather/benzhi-claude-code:20260909-isolated-git"
export CLAUDE_EVAL_MAX_PARALLEL="4"
export CLAUDE_EVAL_HARNESS_VERSION="2.1.263"
export CLAUDE_EVAL_SUBMITTER="张鑫宇"
export CLAUDE_EVAL_ARTIFACT_NODE="/path/to/codex-primary-runtime/dependencies/node/bin/node"
export CLAUDE_EVAL_ARTIFACT_NODE_MODULES="/path/to/codex-primary-runtime/dependencies/node/node_modules"
python3 app.py
```

模型下拉框默认提供 Default、Opus 1M、Sonnet、Sonnet 1M 和 Haiku，并合并当前全局模型及 `CLAUDE_EVAL_MODELS` 中以逗号分隔的自定义模型。默认镜像已配置 `auto_model/urm`，启动脚本同时使用 `ANTHROPIC_MODEL` 传入当前选择。新任务启动时会依次尝试 `CLAUDE_EVAL_DOCKER_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_API_KEY` 和 `~/.claude/settings.json` 里的本机认证配置，只把取到的值传入本题容器，不写入页面、SQLite 或启动脚本。只有自动读取失败时，Terminal 才会要求手动输入。页面只监听 `127.0.0.1`。

运行记录是默认页面，展示并支持按当前对话轮次和更新时间排序，同时可通过编号或关键词、任务类型、项目类别和状态筛选。点击“新建任务”后会在 `0001–2999` 号段预留下一个未使用编号并立即在列表写入“题目生成中”，题面在后台生成并原地补全同一条记录；刷新页面不会丢失进度，同一生成任务未结束时重复请求只返回原记录。题目生成失败时，详情页会保留具体校验原因并提供“沿用原编号重新生成题面”，重试不会消耗新的顺序号。该号段中的顶层 `NNNN-*` 目录会占用普通新项目编号，`3000–3999` 导入号段不会把下一道普通题跳到 3001。点击记录进入详情后，可直接查看完整题面、技术信息和验收命令，并通过浏览器后退或页面按钮返回列表。列表删除只做软删除，不删除轮次证据、本地目录或远端仓库；运行中的记录不可删除，存在子迭代时会返回明确提示。误删可调用 `POST /api/runs/<run_id>/restore` 并发送空 JSON 对象恢复。

运行记录页的“导入现有 0-1 基线”用于登记在本机完成、准备继续出迭代题的项目。页面只需填写一个或多个 `3000–3999` 编号以及保存分组，例如 `3000, 3001`；控制台按编号寻找唯一的顶层项目目录，自动读取 README、项目类别、语言/框架、GitHub commit 和 Docker Compose 验收入口。导入只接受位于 `CLAUDE_EVAL_PROJECTS_ROOT` 内、README 信息足够、工作树干净、`origin` 指向 GitHub、当前 HEAD 与远端 `main` 一致且 `docker compose config --quiet` 通过的仓库。已登记编号重复提交时直接返回原记录；同批其他编号失败不会回滚已经成功的项目，页面会逐项写明缺失目录、README、Git 或 Compose 等原因。导入记录没有 Claude 会话，因此不会伪造 SessionID、PromptID、轨迹或可导出轮次；它只保存 GitHub 初始快照并作为手动迭代和自动补题的根基线，后续目录继续使用 `3000-1`、`3000-2` 等编号。

页面顶部的“自动补题”开关默认关闭，状态和保存目录写入 SQLite，控制台重启后保持不变。可以输入 0.5～168 小时并选择“开启并定时关闭”；关闭时刻同样持久化，页面显示具体时间和剩余时长，到点只停止创建新任务，已经启动的开发任务继续运行。也可以更新或取消定时，改为持续开启。开启后，协调器每 5 秒检查一次容量，把手动题面生成、自动出题、开发、检查和修复共同计入最多 4 个并行槽；已经确认的后续 Bug 修复沿用原任务并优先取得空槽。仍有容量时，系统优先从已完成且有效任务数不足 6 的根项目中继续出题，失败或中断且没有产物的任务不消耗额度，重跑成功只按原任务计一次；同一项目链同时只运行一个独立任务。若 SOLO-QA 将任一轮标为需要返修或废弃，且质检原因明确命中雷同题库、常见小应用或项目/题目/题面/选题/题材不合格，整条根项目链都会退出手动及自动补题选源；普通的内容返修不会误伤项目链。自动链在第 1、4 个位置生成 Feature，第 2、5 个位置生成基于现有代码的 Bug 修复题，第 3、6 个位置可以穿插完整模块构建；每条链最多两个 0-1 完整模块且不能连续出现。Bug 修复题必须先复现三至四个范围适中的真实问题；独立 Bug 修复会话的第一轮题面控制在 300～480 字，依次交代业务范围、用户流程和模块边界，为每个问题写清复现条件、实际表现与正确结果，最后给出逐项回归、既有 Docker Compose 验收及不扩大修复范围的要求，但不提前泄露具体修法。完整模块候选未通过时自动退回范围更小的 Feature；单个来源失败后冷却 30 分钟并继续尝试其他来源，只有连续 3 个自动任务失败才暂停全局补题。没有合适来源时才创建新的顶层 0-1 项目。顶层 0-1 出题每次生成 2 个候选并本地择优，独立复核不通过时只按原题定向改写一次；页面显示候选生成、独立复核和定向改写进度。新题面禁止出现待办清单、任务清单等常见小应用题材，也不再写出容易被题库分类器误判为待办应用的英文占位词，统一改写为“占位实现”。

完成轮次导出页支持按编号或项目、任务类型、难度、资料状态、SOLO-QA 状态和完成日期范围组合筛选；表头全选只作用于当前筛选结果，筛选前已勾选的其他轮次会保留并在计数中注明。单条“删除”和“删除所选”只把完成轮次从导出列表软隐藏，不删除运行记录、项目代码、GitHub 仓库、轨迹证据或 SOLO-QA 远端提交，可通过 `POST /api/exports/turns/restore` 携带 `turn_keys` 恢复。完成轮次导出依赖 Codex 桌面环境附带的 Node.js 与 `@oai/artifact-tool`。默认会从 `~/.cache/codex-runtimes/codex-primary-runtime/dependencies` 读取，也可使用 `CLAUDE_EVAL_ARTIFACT_NODE` 和 `CLAUDE_EVAL_ARTIFACT_NODE_MODULES` 指向兼容运行时。导出失败会返回结构化错误，不会生成空文件或 CSV 伪装的 Excel。

## 提交到 SOLO-QA

首次使用需要安装本地 Chrome 提交助手：

1. 在 Chrome 打开 `chrome://extensions` 并开启“开发者模式”。
2. 点击“加载已解压的扩展程序”。
3. 选择 `/Users/zhangxinyu/claude code/claude-eval-console/chrome-solo-qa-helper`。
4. 登录 <https://solo2.jzxhnh.com>，然后刷新 <http://127.0.0.1:8765/#exports>。

导出页显示“提交助手已连接”后，先点击“同步我的提交”。同步会遍历当前账号的全部提交并读取详情，用 SessionID 与 TurnID/PromptID 精确匹配本地完成轮次；远端已删除的记录会标为“远端未找到”。以后提交前仍会按相同标识回查一次，避免浏览器超时或手工提交造成重复。

选择轮次后点击“提交所选轮次”，确认弹窗中列出的编号、仓库和轮次。助手会动态获取 SOLO-QA 当前表单 fingerprint，将本地任务类型转换成远端规范值，校验并上传不超过 20 MB 的轨迹，再按顺序提交。状态包括未提交、提交中、质检中、质检通过、需要返修、已废弃、提交失败、远端未找到和本地数据已变化。需要返修或提交后本地数据又有改动的记录不会作为新数据重复提交，应从远端详情处理。

扩展的权限只覆盖 `http://127.0.0.1:8765/*` 和 `https://solo2.jzxhnh.com/*`。它使用 Chrome 当前的 SOLO-QA 登录状态，不读取或保存账号、密码和 Cookie；只有在本地页面点击提交并确认后才会上传轨迹和创建记录。

详情页的“复制交付信息”按轮次输出固定字段，包含 Prompt、SessionID、PromptID、纯数字轮次排序、本轮 Git commit、GitHub 初始快照、本轮轨迹文件、环境信息、任务元数据和五维评分；提交人固定为“张鑫宇”。Harness 版本从任务所用 Claude Code 镜像读取并只保存 `2.1.263` 这类纯数字版本，必要时可用 `CLAUDE_EVAL_HARNESS_VERSION` 明确指定。每个轮次卡片也展示 commit、轨迹路径和 SHA-256。评分输入保留本轮头尾原始叙述，并附带覆盖整轮的紧凑工具调用时间线；五项描述按项目复盘口吻分别记录结果、约束、步骤、判断和命令证据，不限制句数，不复述分数，也不接受“均已落地”“准确识别”“阶段顺序清楚”“最终产物可用”等模板化措辞。

## 完成后继续迭代

当 0-1 任务和它的全部 Bug 修复通过检查后，进入该任务详情页顶部的“新建独立迭代会话”，可以选择“完整模块构建（0-1 代码生成）”“平滑扩展（Feature 迭代）”或“现有问题整理（Bug 修复）”，再点击生成按钮。系统固定使用 `gpt-5.6-sol` 读取当前干净的 Git 工作树，以及从根任务到当前版本的完整迭代历史：0-1 类型要求在当前项目中从零形成此前不存在、可独立验收的完整纵向模块，Feature 类型要求复用既有核心对象并平滑扩展现有流程。每轮会保存扩展方向、工程核心、用户主流程、修改模块、复杂维度、接口或操作及状态集合，后续出题会同时比较这些结构化信息和完整题面，拒绝只换名称的重复状态、闸门、审批、导出或错误处理。已经失败、停止或中断且没有形成有效产物的迭代仍保留在历史中，但标记为 abandoned，不占六轮配额也不永久阻塞项目链；再次发起时系统重新读取远端 `main`，只选择与远端最新提交一致的最近成功、干净工作区作为代码基线。运行中的迭代仍会阻止重复创建；如果远端最新提交找不到对应的成功工作区，系统会停止创建而不会从旧代码分叉。

Feature 与完整模块使用硬范围预算控制实现负担，但不在题面中写难度标签：题面统一为 300～480 字、四至六个完整句子、分号不超过两个且单句不超过 120 字；只涉及三至四个逻辑模块、一个工程核心、一条用户主流程、最多两个新增接口或用户操作、最多一组新增状态、一项复杂机制和三至四个验收场景。Feature 不得增加独立运行组件；完整模块最多增加一个独立运行组件，且不能与复杂机制同时出现。新的分布式协调、密码学证明、自定义二进制协议、复杂求解器或完整跨进程恢复不能作为迭代核心。生成结果先通过本地结构化硬校验，独立复核再从实际题面重新提取范围，不采信候选自报的数量；少报、合并机制、成功历史实质重复或模板化表达都会被退回。失败题面不被当作已经实现的功能，可以根据当前代码重新设计，但不会原样重发。题面按业务因果自然组织，不机械拼接数据库、接口、页面与测试字段，不连续堆叠命令句，不使用“沿用既有不变量”“其余失败沿用错误信封”等模板短语，也不在结尾集中罗列通用清单。内部范围筛选条件不会写进题面，出题模型与页面选择的开发模型相互独立。

独立 Bug 修复任务会先在最新成功代码上检查并复现问题，选择集中在同一用户流程、预计修改范围为小或中的三至四个真实 Bug。第一轮题面把每个问题写成一句客户可读的话并连成一个自然段，只描述触发场景、错误表现和正确结果，不给解决方法、技术实现或通用验收清单；无法稳定复现、属于环境故障或已经在成功历史中修好的问题不会进入题面。自动补题的六轮链默认在第 2、5 轮安排 Bug 修复，第 3、6 轮仍可安排完整模块，其余位置使用 Feature。开发完成后的检查若仍发现 Bug，后续修复轮会从自然交接开头中稳定选择一种，把每个 Bug 编号后用中文分号拼成同一个物理行，避免终端把一次题面拆成多条消息。

Bug 检查的详细复现步骤、实际结果、预期结果和命令证据保存在检查记录中，不再全部塞进发给开发者的题面。每个 Bug 的客户摘要只用一句话说明触发场景、错误表现和正确结果，不自行添加标题、序号、引号、实现术语或通用测试清单；系统在组装修复题面时统一添加自然开头和编号，并保持整段无换行。同一任务和轮次的开头选择保持稳定，不同任务会自然轮换表达。

点击后接口立即把出题放入后台，任务状态和当前阶段同时写入 SQLite；页面刷新或控制台重启后会继续识别并恢复，运行中也可点“取消生成”。再次选择同一类型只会等待同一后台任务，已经创建过同类型产出时直接返回原运行记录。Feature、Bug 修复与 0-1 共用每条链最多 6 个有效独立任务的额度；完整模块最多两个且不能连续创建，手动选择和自动补题执行相同配额与全局四槽限制。每次生成题面和创建目录前，系统都会读取 GitHub 远端 `main` 的实际 HEAD，并在同一迭代链中寻找拥有该提交、工作树干净且代码轮次已经完成的最新记录；新记录的 `source_run_id`、GitHub 初始快照和克隆 commit 全部指向这个最新节点。链上仍有运行任务，或远端最新提交找不到对应的干净工作区时会停止创建并给出明确错误，不再回退到根项目旧提交。生成通过后，系统会立即新建一条运行记录，打开新 Terminal，启动新容器和新 SessionID，再把该最新 Git commit 克隆到新的 `/workspace` 并执行需求；不续接旧对话，也不预先改变来源任务。生成或复核失败时不会创建半成品运行记录，错误会写入来源任务时间线并允许再次点击。任务完成后如果检查出真实且与本轮需求直接相关的 Bug，只在这个新 SessionID 中继续修复和复查；无关历史问题只记录为质量建议，不进入修复题面。

新任务默认保存在 `/Users/zhangxinyu/claude code/zzzz`，也可以在页面中选择该根目录内的其他子目录。从空仓库创建的本地项目文件夹使用四位顺序号，例如 `0001-incident-handoff-board`、`0002-data-quality-console`；基于现有快照的新迭代使用源编号下的独立序号，例如 `0002-1-incident-handoff-board`、`0002-2-incident-handoff-board`。两类编号都不影响 GitHub 仓库名。
